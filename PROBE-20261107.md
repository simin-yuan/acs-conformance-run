# Probe — 2026-11-07: can the client be wired at all?

**Status:** wiring probe. Recorded before any ACS Guardian was in the path.
**Why it exists:** a run described in `PREREGISTRATION.md` is only worth promising if the client can be pointed at a controllable endpoint. This records that check, including one result that bears on P1.

`server.py` in the same repository speaks Chat Completions and the Responses API only, so a Messages client cannot be pointed at it at all. That is why the endpoint had to be written rather than reused.

## Result

The client connected, requested `/length/v1/messages`, and received an SSE stream in which the tool-call argument stops mid-string inside line 17. What it then did:

| Observed | Value |
|---|---|
| Tool call surfaced | `Write`, with `input.__unparsedToolInput` present, 922 raw bytes |
| Tool result | `is_error: true`, "InputValidationError: Write was called with input that could not be parsed" |
| File created | no (`report.txt` absent from the working directory) |
| Turn count | 2 |

## What this does and does not show

It shows the wiring works: a real client, a controllable endpoint, one injected fault, and a recorded outcome. It does not show anything about ACS — no Guardian was running, so no hook observed this step.

**It also bears on P1, and the honest reading is that P1's premise does not hold for this client.** P1 predicted that the client repairs the truncated argument before the hook fires, so the Guardian receives a well-formed argument it cannot distinguish from an intended one. This client did the opposite: it refused to execute and reported a parse failure. The action never happened, so there was nothing for a Guardian to govern — and nothing for it to miss.

P1 stays in the preregistration unedited. The report will record it as refuted for this client on this record, with the date above, rather than restate it as if it had held.
